# Задача 009: Вкладка BLE логів контролера

## Мета

Додати у **Сервісну консоль** вкладку для перегляду BLE логів, які контролер надсилає через notifications.

Це має бути інструмент для польової діагностики контролера без підключення serial monitor або зовнішнього лог-сервера.

Усі видимі користувачу тексти мають бути українською мовою.

## Контекст

Задача 008 створює **Сервісну консоль** із вкладками. Ця задача додає другу вкладку для live BLE logs із контролера.

У застосунку вже є BLE infrastructure для onboarding:

- discovery;
- pairing/session;
- BLE read/write;
- controller access bootstrap.

Потрібно використати існуючий BLE service/session підхід, а не створювати паралельний BLE stack у widget layer.

## Обсяг задачі

### 1. Вкладка

Додати вкладку **BLE логи** у **Сервісну консоль**.

Вкладка має показувати:

- стан BLE підключення до активного контролера;
- стан підписки на notifications;
- список отриманих log records;
- час отримання кожного запису на телефоні;
- текст log message з контролера.

### 2. Підключення до контролера

Потрібно:

- використовувати активний `WateringHub.bleDeviceId`;
- не запускати BLE discovery, якщо активний controller profile уже має BLE device id;
- коректно показати стан, якщо BLE device id відсутній;
- мати дію **Підключитися**;
- мати дію **Відключитися**;
- не ламати onboarding BLE flow, якщо користувач відкрив сервісну консоль після завершеного onboarding.

Якщо поточна BLE abstraction не підтримує повторне підключення для сервісних сценаріїв, додати мінімальний repository/controller шар для цього flow.

### 3. BLE notifications

Реалізувати підписку на characteristic із логами контролера згідно з firmware BLE API.

Потрібно:

- використати існуючі BLE constants, якщо characteristic уже описаний;
- якщо constant відсутній, додати його у спільне місце BLE constants;
- декодувати payload у текстовий log message;
- обробляти chunked або line-based payload так, як описано firmware API;
- не падати, якщо payload не є валідним UTF-8 або має неочікуваний формат;
- записувати локальний timestamp отримання на телефоні.

Якщо firmware API для log notifications ще не зафіксований у коді, у задачі потрібно синхронізувати constants із документацією контролера перед реалізацією.

### 4. UI logs list

Для кожного BLE log record показувати:

- час отримання;
- текст повідомлення;
- optional level/source, якщо firmware явно передає ці поля;
- raw text fallback, якщо payload неструктурований.

Потрібно:

- показувати найновіші записи зверху або мати зрозумілий auto-scroll до нових записів;
- обмежити in-memory кількість записів, щоб екран не ріс безконтрольно;
- не зберігати BLE logs у persistent storage у цій задачі;
- дати дію **Очистити** для локального списку отриманих BLE logs;
- підтвердження для clear не обов'язкове, якщо очищується тільки поточний volatile buffer.

### 5. Error handling

Показувати українською:

- BLE device id відсутній;
- не вдалося підключитися;
- контролер відключився;
- не вдалося підписатися на notifications;
- отримано неочікуваний payload.

Технічні деталі BLE помилок потрібно писати в `DiagnosticsLog`, а не показувати довгим текстом у вкладці.

### 6. Не входить у задачу

- server-side logs;
- remote log settings;
- export/share BLE logs;
- persistent storage BLE logs;
- фільтри по level/source;
- зміна Modbus адреси;
- BLE onboarding redesign.

## Критерії готовності

Задача готова, якщо:

- у **Сервісній консолі** є вкладка **BLE логи**;
- вкладка вміє підключитися до активного контролера через BLE;
- вкладка підписується на BLE notifications логів;
- отримані повідомлення показуються з часом отримання;
- локальний список BLE logs можна очистити;
- reconnect/disconnect стани відображаються українською;
- BLE помилки пишуться в `DiagnosticsLog`;
- BLE logs не зберігаються persistent;
- onboarding flow не ламається;
- проєкт проходить `flutter analyze`;
- додані або оновлені тести для controller/state logic і базового UI вкладки.
