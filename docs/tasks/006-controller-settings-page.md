# Задача 006: Controller settings page

## Мета

Реалізувати повноцінну сторінку налаштувань контролера на базі наявного прототипу. Сторінка має дозволяти переглядати і змінювати всі доступні налаштування контролера через локальний HTTPS API.

Увесь інтерфейс сторінки, назви секцій, назви полів, підказки, помилки, повідомлення про стан і кнопки мають бути українською мовою.

Після збереження settings контролер перезавантажується. Додаток має коректно провести користувача через стан reboot, через 4 секунди почати перепідключення, після відновлення зв'язку повторно зчитати settings, показати повідомлення про успішне відновлення з'єднання і повернути користувача на головний екран.

## Контекст із ТЗ

Settings контролера є джерелом технічної конфігурації системи поливу. У задачі 005 додаток вже має читати settings через `GET /api/settings`, парсити повний snapshot, будувати device objects і тримати актуальний settings state в пам'яті.

Settings зчитуються глобально при запуску додатку. Сторінка налаштувань не є власником первинного читання settings і не повинна перечитувати settings тільки через сам факт переходу на сторінку. Вона відображає вже наявний глобальний snapshot або стан, що settings ще не були успішно завантажені.

Якщо додаток довго перебуває в пам'яті, питання повторної синхронізації settings має вирішуватись глобальним lifecycle/recovery механізмом додатку, а не сторінкою налаштувань. Оскільки очікується, що налаштування змінює тільки цей мобільний додаток, сам по собі час життя snapshot у пам'яті не є підставою вважати його застарілим. Повторне читання settings потрібне після подій, які можуть змінити або поставити під сумнів snapshot: запуск додатку, відновлення з'єднання після втрати, успішне збереження settings із reboot контролера, BLE/HTTPS recovery, зміна активного контролера або явний глобальний refresh.

Ця задача додає повний UI для редагування settings і збереження змін через `PUT /api/settings`.

Збереження settings виконується через HTTPS:

```http
PUT /api/settings
Authorization: Bearer <apiAccessToken>
Content-Type: application/json
```

Після успішного `PUT /api/settings` контролер застосовує конфігурацію і переходить у reboot. Через це одразу після успішного response додаток не повинен очікувати стабільного HTTPS-з'єднання.

## Обсяг задачі

### 1. Settings screen entry point

Додати або завершити екран налаштувань контролера.

Потрібно:

- використати наявний прототип сторінки як основу;
- відкривати сторінку з головного екрану або поточного місця, де вже передбачений перехід до налаштувань;
- не запускати `GET /api/settings` тільки через відкриття сторінки;
- читати settings snapshot із глобального app/settings state;
- якщо settings snapshot вже є, одразу показувати форму;
- якщо settings snapshot відсутній, показати українською стан, що налаштування ще не завантажені глобальним startup/recovery flow;
- якщо глобальний settings sync завершився помилкою до відкриття сторінки, показати цю помилку українською без локальної кнопки повторного читання на сторінці;
- не показувати сирий JSON користувачу.

### 2. Повна форма налаштувань

Форма має відображати всі settings, які підтримує поточна typed schema `ControllerSettings`.

Поля мають бути згруповані в логічні секції. Глобальні інтервали зчитування мають бути поруч із розділами відповідних пристроїв, а датчики вологості мають іти перед клапанами, бо клапан прив'язується до вже доданого датчика.

Порядок секцій:

- **Загальні налаштування**
  - максимальний час ручного відкриття клапана;
  - вологість, нижче якої починати полив;
  - вологість, вище якої зупиняти полив;
  - режим старту поливу;
  - початок вікна поливу;
  - кінець вікна поливу;
  - тривалість поливу однієї зони;
  - затримка перед повторною спробою поливу зони.
- **Віддалені логи**
  - URL сервера для логів і метрик;
  - token для відправки логів і метрик.
- **Датчики вологості грунту**
  - інтервал зчитування датчиків вологості у режимі очікування;
  - інтервал зчитування датчиків вологості під час поливу;
  - список датчиків;
  - Modbus address;
  - назва датчика.
- **Датчик тиску**
  - інтервал зчитування датчика тиску у режимі очікування;
  - інтервал зчитування датчика тиску під час поливу;
  - увімкнений або відсутній датчик;
  - Modbus address;
  - назва датчика.
- **Магістральний лічильник води**
  - інтервал зчитування лічильників води у режимі очікування;
  - інтервал зчитування лічильників води під час поливу;
  - увімкнений або відсутній лічильник;
  - GPIO pin;
  - назва;
  - літрів за один імпульс.
- **Лічильники води гілок**
  - список лічильників;
  - GPIO pin;
  - назва;
  - літрів за один імпульс.
- **Клапани**
  - список клапанів;
  - GPIO pin;
  - назва клапана;
  - прив'язаний датчик вологості зі списку вже доданих датчиків.

Якщо typed schema settings буде розширена, форма має бути оновлена так, щоб користувач міг переглядати і змінювати всі нові підтримувані поля.

### 3. Поведінка полів форми

Потрібно використовувати відповідні типи контролів:

- числові поля для секунд, відсотків, GPIO pin, Modbus address і `litersPerTick`;
- текстові поля для назв;
- password/secret-поле для token віддалених логів;
- перемикач або segmented control для `wateringStartMode`;
- time picker або пара числових полів для `TimeOfDaySetting`;
- dropdown/select для прив'язки клапана до існуючого датчика вологості; користувач обирає датчик за зрозумілою назвою, а не вручну вводить Modbus address;
- toggle або action-кнопки для додавання/видалення optional sensor/counter об'єктів.

Форма має підтримувати:

- додавання клапанів;
- видалення клапанів;
- додавання датчиків вологості;
- видалення датчиків вологості;
- додавання лічильників води гілок;
- видалення лічильників води гілок;
- увімкнення або видалення датчика тиску;
- увімкнення або видалення магістрального лічильника води.

Для destructive дій у формі потрібне зрозуміле підтвердження українською, якщо дія може призвести до втрати введених користувачем даних або поламати прив'язки.

### 4. Валідація

Форма має валідовувати дані до відправки на контролер.

Мінімальні правила:

- числові інтервали в секундах: `1..2147483`;
- humidity percent: `0..100`;
- stop humidity threshold має бути більшим за start humidity threshold;
- `wateringStartMode` має бути `immediately` або `withinWateringWindow`;
- для `withinWateringWindow` початок і кінець вікна поливу обов'язкові;
- `TimeOfDaySetting.hour`: `0..23`;
- `TimeOfDaySetting.minute`: `0..59`;
- Modbus address: `1..247`;
- `litersPerTick` має бути додатним скінченним числом;
- назви не мають бути порожніми;
- GPIO pins не мають конфліктувати між клапанами і лічильниками води;
- Modbus addresses не мають конфліктувати між датчиками вологості і датчиком тиску;
- кожен клапан має посилатися на існуючий датчик вологості;
- кількість клапанів, датчиків вологості і лічильників гілок не має перевищувати firmware limit `32`.

Кнопка **Зберегти** має бути неактивною, якщо:

- settings snapshot відсутній у глобальному app/settings state;
- форма невалідна;
- немає змін відносно останнього зчитаного snapshot;
- вже триває збереження або перепідключення.

Помилки валідації потрібно показувати біля відповідних полів або секцій українською мовою.

### 5. Збереження settings

Додати repository/use case для збереження settings або розширити наявний settings repository.

Потрібно:

- зібрати typed `ControllerSettings` з форми;
- не формувати JSON у widget layer;
- виконати `PUT /api/settings`;
- додати `Authorization: Bearer <apiAccessToken>`;
- не логувати bearer token і remote log token;
- обробити HTTP statuses `200`, `400`, `401`, `404`, `413`, `500`, `503`;
- показати користувачу помилку українською, якщо збереження не вдалося;
- залишити користувача на сторінці налаштувань після помилки збереження;
- не оновлювати in-memory settings як успішні, якщо `PUT` завершився помилкою.

Під час активного збереження:

- заблокувати редагування форми;
- заблокувати повторне натискання **Зберегти**;
- показати стан **Зберігаємо налаштування...**.

### 6. Reboot and reconnect flow

Після успішного `PUT /api/settings`:

- показати стан **Контролер перезавантажується...**;
- заблокувати форму;
- не виконувати миттєвий reconnect;
- почекати 4 секунди;
- після 4 секунд почати спроби перепідключення до контролера через HTTPS;
- показати стан **Відновлюємо з'єднання з контролером...**.

Механіка reconnect:

- використовувати останню відому IP-адресу і controller `apiAccessToken`;
- виконувати легку перевірку HTTPS доступності або одразу `GET /api/settings`;
- повторювати спроби, якщо контролер ще недоступний;
- мати timeout на одну спробу;
- мати загальний timeout або зрозумілу можливість ручної повторної спроби, якщо reconnect довго не вдається;
- коректно обробити `401` як втрату/невалідність token;
- коректно обробити network/TLS/controller unavailable як тимчасову недоступність під час reboot.

Після успішного reconnect:

- виконати `GET /api/settings`;
- розпарсити новий settings snapshot;
- оновити in-memory `ControllerSettings`;
- перебудувати device objects;
- перерахувати `configurationState`;
- перевести hub state в `online`;
- показати повідомлення **З'єднання з контролером відновлено**;
- автоматично повернути користувача на головний екран.

Якщо reconnect не вдався:

- залишити користувача на сторінці налаштувань або на спеціальному стані відновлення;
- показати зрозуміле повідомлення українською;
- дати кнопку повторної спроби;
- не показувати старі settings як щойно підтверджені.

### 7. Navigation safety

Якщо користувач має незбережені зміни і намагається покинути сторінку:

- показати підтвердження українською;
- дати варіанти залишитися, вийти без збереження або зберегти, якщо форма валідна.

Під час збереження, reboot і reconnect не дозволяти випадково перервати flow без явного підтвердження.

### 8. State integration

Оновити state для flow збереження settings так, щоб UI не тримав бізнес-стан тільки локально у widget.

Ці стани не є глобальними станами settings sync. Вони описують саме flow редагування, збереження, reboot і reconnect після натискання **Зберегти**.

Потрібні стани save flow:

- `ready`;
- `dirty`;
- `invalid`;
- `saving`;
- `rebooting`;
- `reconnecting`;
- `reconnected`;
- `saveFailed`;
- `reconnectFailed`.

Назви можуть бути адаптовані до існуючої архітектури, але поведінка має бути явно покрита.

Потрібно уникати дублювання одного й того ж стану в декількох boolean-прапорцях, якщо в проєкті вже використовується enum/state object.

Глобальний settings sync state із задачі 005 залишається окремим і відповідає за startup/recovery читання settings. Сторінка налаштувань тільки споживає його snapshot та помилку, якщо snapshot відсутній.

### 9. Тести

Додати або оновити тести для:

- побудови payload для `PUT /api/settings`;
- валідації settings форми;
- заборони збереження невалідної форми;
- успішного save flow;
- помилки save flow;
- очікування 4 секунди перед reconnect;
- reconnect після reboot;
- повторного `GET /api/settings` після reconnect;
- повернення на головний екран після успішного reconnect;
- показу українських повідомлень у ключових станах;
- відсутності локального `GET /api/settings` при самому відкритті сторінки, якщо snapshot уже є в глобальному state.

Для timer/reconnect flow використовувати fake async або інший контрольований механізм часу, щоб тести не чекали реальні 4 секунди.

## Критерії готовності

- Користувач може відкрити сторінку налаштувань контролера.
- Відкриття сторінки саме по собі не запускає повторне читання settings.
- Користувач може переглянути всі settings, які підтримує typed schema.
- Користувач може змінити всі settings, які підтримує typed schema.
- Форма повністю українською мовою.
- Форма має секції, зрозумілі назви полів і українські повідомлення про помилки.
- Валідація не дозволяє відправити явно невалідну конфігурацію.
- `PUT /api/settings` виконується через HTTPS із bearer token.
- Після помилки збереження користувач залишається на сторінці і бачить помилку.
- Після успішного збереження сторінка переходить у стан reboot.
- Через 4 секунди після успішного збереження додаток починає reconnect.
- Після reconnect додаток повторно виконує `GET /api/settings`.
- Після успішного зчитування нових settings оновлюється app state.
- Користувач бачить повідомлення **З'єднання з контролером відновлено**.
- Після успішного reconnect користувач автоматично повертається на головний екран.
- Старі settings не показуються як актуальні, якщо reconnect або повторне зчитування settings не завершилося успішно.
- Основна логіка покрита unit/widget tests.
