# Задача 008: Сервісна консоль і перегляд діагностичних логів

## Мета

Створити окрему сторінку **Сервісна консоль** для діагностики, обслуговування і допоміжних інженерних дій.

У цій задачі потрібно додати базову сторінку з вкладками і реалізувати першу вкладку: перегляд локальних діагностичних логів додатку.

Сторінка не є частиною щоденного сценарію поливу, але має бути доступною з будь-якого основного місця застосунку. Діагностичні повідомлення можуть писатися з головного екрана, BLE onboarding, controller access recovery, settings flow та інших сценаріїв, тому користувач має мати шлях до перегляду логів незалежно від поточного екрана.

Усі видимі користувачу тексти мають бути українською мовою.

## Контекст

У додатку вже є `DiagnosticsLog`, який зберігає технічні деталі помилок комунікації і діагностичні повідомлення без показу цих деталей у основному UI.

Основний UI має залишатися лаконічним:

- для користувача достатньо повідомлення на рівні **Помилка комунікації з контролером**;
- технічні причини, HTTP status, response body, exception class і schema mismatch details потрібні для дебагу та експлуатаційної діагностики;
- bearer token, remote log token та інші секрети не мають потрапляти в UI або logs.

Ця задача додає екран, де ці діагностичні записи можна переглянути без підключення зовнішнього логера.

## Обсяг задачі

### 1. Entry point

Додати глобально доступний перехід на **Сервісну консоль**.

Потрібно:

- забезпечити доступ із головного екрана;
- забезпечити доступ із BLE onboarding екранів;
- забезпечити доступ із controller access / recovery екранів;
- забезпечити доступ зі сторінки налаштувань контролера;
- забезпечити доступ з error/fatal state екранів, якщо app shell уже дозволяє показувати такі дії;
- не робити доступ залежним від наявності активного `WateringHub`, IP, token або успішного onboarding.

Рекомендований варіант реалізації:

- винести action відкриття **Сервісної консолі** у спільний app-level widget або helper;
- додавати його в `AppBar`/actions основних екранів як compact icon/menu item;
- для екранів без `AppBar` додати лаконічний вторинний action, який не конкурує з основним сценарієм;
- не додавати великий CTA на головний dashboard;
- не змішувати сервісні дії з daily-use картками девайсів.

Візуально дія має бути однаковою по застосунку:

- label/tooltip: **Сервісна консоль**;
- бажано icon: tools/build або bug/report, залежно від наявних іконок у Flutter Material;
- якщо використовується overflow menu, item має називатися **Сервісна консоль**.

### 2. Shell сторінки

Створити окремий screen/widget для **Сервісної консолі**.

Потрібно:

- `AppBar` title: **Сервісна консоль**;
- layout із вкладками;
- перша вкладка: **Діагностика**;
- структура має дозволяти додати вкладки задач 009 і 010 без переписування сторінки;
- стан вкладок має бути локальним UI state, якщо немає потреби в глобальному state.

Не потрібно робити landing/hero/marketing screen. Першим екраном має бути робочий інструмент.

### 3. Вкладка діагностичних логів

Вкладка **Діагностика** має показувати записи з `DiagnosticsLog`.

Для кожного запису відображати:

- час події;
- коротке повідомлення;
- HTTP method, якщо є;
- host, якщо є;
- path, якщо є;
- HTTP status code, якщо є;
- response body, якщо є;
- exception class, якщо є;
- details, якщо є.

Потрібно:

- показувати записи у зворотному хронологічному порядку;
- не показувати порожні поля;
- довгі response body/details показувати переносами або в expandable area;
- забезпечити читабельність на мобільному екрані;
- не вкладати cards у cards.

### 4. Оновлення і очищення

Додати дії:

- **Оновити** - перечитати поточні записи з `DiagnosticsLog`;
- **Очистити** - очистити тимчасовий лог.

Для **Очистити** потрібне підтвердження українською, бо дія видаляє діагностичний контекст.

Якщо поточна реалізація `DiagnosticsLog` ще не підтримує clear, додати метод у інтерфейс і реалізацію.

### 5. Empty state

Якщо записів немає, показати лаконічний empty state:

**Діагностичних записів немає.**

Не показувати технічні placeholders або mock records.

### 6. Безпека даних

Потрібно:

- не показувати bearer token;
- не показувати remote log token;
- не логувати повні Authorization headers;
- не додавати копіювання всіх логів у clipboard у цій задачі, якщо немає маскування секретів.

### 7. Не входить у задачу

- BLE logs із контролера;
- зміна Modbus адреси;
- export/share logs;
- persistent storage для diagnostics log;
- server-side log upload;
- фільтри і пошук по логах;
- grouping по controller/session.

## Критерії готовності

Задача готова, якщо:

- у застосунку є сторінка **Сервісна консоль**;
- **Сервісна консоль** доступна з головного екрана;
- **Сервісна консоль** доступна з BLE onboarding;
- **Сервісна консоль** доступна з controller access / recovery flow;
- **Сервісна консоль** доступна зі сторінки налаштувань контролера;
- доступ до **Сервісної консолі** не залежить від успішного підключення до контролера;
- сторінка має вкладку **Діагностика**;
- вкладка показує записи з `DiagnosticsLog`;
- записи відображають час, повідомлення і доступні технічні поля без порожніх рядків;
- записи відсортовані від найновішого до найстарішого;
- є дія **Оновити**;
- є дія **Очистити** з підтвердженням;
- empty state українською показується, коли записів немає;
- секрети не показуються і не логуються;
- структура сторінки готова для вкладок задач 009 і 010;
- проєкт проходить `flutter analyze`;
- додані або оновлені тести для basic rendering, empty state і clear action.
