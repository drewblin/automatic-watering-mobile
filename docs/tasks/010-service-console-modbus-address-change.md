# Задача 010: Вкладка зміни Modbus адреси девайса

## Мета

Додати у **Сервісну консоль** вкладку для зміни Modbus адреси підключеного девайса.

Це сервісна дія для первинного налаштування або заміни датчиків. Вона має бути відокремлена від звичайних налаштувань контролера, бо неправильна адреса може зробити девайс недоступним для контролера.

Усі видимі користувачу тексти мають бути українською мовою.

## Контекст

Задача 008 створює **Сервісну консоль** із вкладками. Ця задача додає вкладку для сервісної Modbus операції.

Звичайна сторінка налаштувань контролера оперує вже відомими адресами девайсів. Зміна фізичної Modbus адреси девайса є окремою дією, яку потрібно виконувати обережно і явно.

## Обсяг задачі

### 1. Вкладка

Додати вкладку **Modbus адреса** у **Сервісну консоль**.

Вкладка має містити:

- короткий поточний стан підключення до контролера;
- вибір або введення поточної адреси девайса;
- введення нової адреси;
- дію **Змінити адресу**;
- результат останньої операції.

Не показувати цю дію на головному dashboard або у cards девайсів.

### 2. API / транспорт

Реалізувати виклик firmware API для зміни Modbus адреси через наявний доступ до контролера.

Потрібно:

- використати documented endpoint або BLE command із firmware API;
- тримати transport logic поза widget layer;
- не дублювати HTTP/BLE client code у UI;
- повертати typed result;
- писати технічні деталі помилок у `DiagnosticsLog`.

Якщо firmware API передбачає `sensorId` або device type, модель запиту має явно це відображати. Якщо API працює тільки з current/new address, UI не має вигадувати зайві поля.

### 3. Валідація

Перед відправкою потрібно валідовувати:

- поточна адреса: `1..247`;
- нова адреса: `1..247`;
- нова адреса відрізняється від поточної;
- операція не виконується повторно, поки попередній запит триває.

Якщо в app state є актуальні controller settings, бажано попереджати, якщо нова адреса вже використовується іншим налаштованим Modbus девайсом.

Попередження про конфлікт не має блокувати дію автоматично, якщо firmware/service scenario допускає ремонтну операцію, але користувач має явно підтвердити ризик.

### 4. Підтвердження

Перед зміною адреси показати confirmation dialog українською.

Dialog має пояснювати:

- яку адресу буде змінено;
- на яку адресу буде змінено;
- що після зміни потрібно оновити налаштування контролера, якщо девайс уже був прив'язаний у settings.

Primary action: **Змінити адресу**.

Secondary action: **Скасувати**.

### 5. Після успішної зміни

Після успіху потрібно:

- показати transient notification або inline success state;
- запропонувати перейти до налаштувань контролера, якщо потрібно оновити прив'язку адреси;
- не змінювати `ControllerSettings` автоматично без явного збереження settings через settings flow;
- не підміняти current settings snapshot локально.

### 6. Error handling

Показувати українською:

- не вдалося зв'язатися з контролером;
- девайс на поточній адресі не відповідає;
- нова адреса некоректна;
- контролер повернув помилку;
- операція не підтверджена або скасована.

Технічні деталі transport/schema/controller errors потрібно писати в `DiagnosticsLog`.

### 7. Не входить у задачу

- автоматичне сканування Modbus bus;
- bulk зміна адрес;
- persistent history сервісних операцій;
- автоматична зміна `ControllerSettings`;
- переписування сторінки налаштувань контролера;
- BLE logs;
- export діагностики.

## Критерії готовності

Задача готова, якщо:

- у **Сервісній консолі** є вкладка **Modbus адреса**;
- користувач може ввести поточну і нову адресу;
- адреси валідовуються в діапазоні `1..247`;
- однакова поточна і нова адреса блокується validation error;
- перед виконанням показується confirmation dialog;
- transport/API logic винесена з widget layer;
- успіх і помилки показуються українською;
- технічні деталі помилок пишуться в `DiagnosticsLog`;
- після успіху settings snapshot не змінюється неявно;
- є зрозумілий шлях перейти до налаштувань контролера для оновлення прив'язок;
- проєкт проходить `flutter analyze`;
- додані або оновлені тести для validation, confirmation flow і API/controller interaction.
