# Технічне завдання мобільного додатку Automatic Watering

## 1. Призначення додатку

Мобільний додаток призначений для первинного налаштування, моніторингу та керування контролером автоматичного поливу `Automatic Watering Hub`.

Додаток має закривати три основні потреби користувача:

- підключити контролер до домашньої Wi-Fi мережі;
- налаштувати систему поливу, сенсори, клапани, лічильники та правила автоматичного поливу;
- контролювати стан системи через поточні показники, графіки, логи, push-сповіщення та ручний запуск поливу.

Додаток не є самостійним backend-сервісом і не виконує логіку автоматичного поливу. Він є клієнтом до контролера і, за наявності cloud-функцій, до серверного API.

## 2. Загальна концепція

Додаток має виглядати як утилітарний інструмент для керування IoT-системою: спокійний, технічний, зрозумілий, з пріоритетом на швидке зчитування стану системи та безпечне виконання дій.

Перший екран після запуску має вести користувача до актуального стану пристрою: або до робочої схеми підключеного контролера, або до сценарію додавання/відновлення підключення.

Основна ідея інтерфейсу:

- робочий екран показує графічну схему ділянки з зонами поливу, сенсорами та поточним станом;
- вкладки або нижня навігація ведуть до основних зон роботи;
- критичні дії, які можуть запустити полив або перезавантажити контролер, мають явне підтвердження;
- технічні параметри мають бути доступні, але не повинні перевантажувати головний екран.

## 3. Канали взаємодії

Додаток працює з трьома каналами.

### 3.1. BLE

BLE використовується для первинного налаштування та відновлення доступу:

- пошук пристрою `Automatic Watering Hub`;
- pairing із 6-значним passkey;
- читання та запис Wi-Fi settings;
- читання IP-адреси контролера;
- читання `apiAccessToken`;
- перегляд live BLE log notifications як допоміжний діагностичний канал.

Wi-Fi credentials не мають передаватися через HTTPS API. Вони налаштовуються тільки через BLE.

### 3.2. Локальний HTTPS API контролера

Локальний HTTPS API використовується для основного керування контролером у локальній мережі:

- читання та збереження settings;
- отримання останніх значень сенсорів;
- ручний запуск клапана на заданий час;
- зміна Modbus slave address пристрою.

Кожен запит до контролера має використовувати bearer token, отриманий через BLE. Додаток має зберігати цей token у захищеному сховищі.

### 3.3. Server API

Server API використовується для функцій, які не можуть надійно працювати тільки через локальну мережу:

- історія логів;
- push-сповіщення по логах;
- останні метрики з сервера;
- time series для графіків;
- summary по метриках за період.

Server API використовує окремий mobile session token. Його не можна змішувати з `apiAccessToken` контролера або ingest token контролера.

## 4. Основні сутності

### 4.1. Пристрій

Пристрій у додатку відповідає одному контролеру `Automatic Watering Hub`.

Для пристрою додаток зберігає:

- display name;
- BLE device id;
- останню відому IP-адресу;
- controller `apiAccessToken`;
- ознаку cloud-функцій та server `deviceId`, якщо вони налаштовані;
- схему ділянки: будинок, межі зон, розташування сенсорів, лічильників води і прив'язки елементів схеми до settings контролера;
- останній відомий стан підключення.

### 4.2. Зона поливу

Зона поливу відповідає клапану з `valveSettings`.

Зона має:

- назву;
- GPIO pin клапана;
- прив'язаний soil sensor;
- контур або область на схемі ділянки;
- поточні або останні відомі показники вологості/температури;
- дію ручного запуску поливу.

### 4.3. Сенсори та лічильники

Додаток має показувати такі типи вимірювань:

- тиск;
- витрата води за останні 5 хвилин для water counters;
- температура грунту;
- вологість грунту.

Значення сенсора або лічильника може бути недоступним. UI має явно відрізняти `null`/помилку читання від нульового значення.

### 4.4. Налаштування поливу

Глобальні налаштування визначають:

- частоту читання сенсорів у режимі очікування та під час поливу;
- максимальний час ручного відкриття клапана;
- пороги старту та зупинки автоматичного поливу за вологістю;
- режим старту автоматичного поливу;
- вікно дозволеного поливу;
- тривалість поливу зони;
- затримку повторної спроби поливу.

## 5. Навігація

Рекомендована структура основної навігації:

- `Plan` - графічна схема ділянки, поточний стан зон, сенсорів і швидкі дії;
- `Zones` - список зон поливу та ручне керування клапанами;
- `Charts` - графіки метрик за період;
- `Logs` - live та історичні логи;
- `Settings` - налаштування контролера, Wi-Fi, cloud, сенсори, клапани, сервісні дії.

Для першого запуску або відсутнього пристрою використовується окремий onboarding flow:

- пошук контролера;
- pairing;
- налаштування Wi-Fi;
- очікування reboot;
- отримання IP та token;
- перевірка локального HTTPS доступу;
- базове налаштування системи.

## 6. Екрани та призначення

### 6.1. Device List / Connection State

Екран потрібен, якщо пристрій ще не додано або збережений пристрій недоступний.

Функції:

- показати збережені контролери;
- показати стан доступності;
- запустити додавання нового контролера;
- спробувати відновити IP/token через BLE;
- перейти до робочої схеми доступного контролера.

На першому етапі допускається підтримка одного основного контролера, але структура додатку має не блокувати майбутню підтримку кількох пристроїв.

### 6.2. Onboarding / First Setup

Flow первинного налаштування має бути покроковим.

Кроки:

1. Сканування BLE-пристроїв.
2. Підключення та pairing.
3. Введення або оновлення Wi-Fi credentials.
4. Збереження Wi-Fi settings.
5. Очікування перезавантаження контролера.
6. Повторне BLE-підключення.
7. Отримання IP-адреси та API token.
8. Перевірка HTTPS-з'єднання.
9. Перехід до базового налаштування системи або схеми ділянки.

Якщо IP дорівнює `0.0.0.0`, додаток має показувати стан очікування і давати можливість повернутися до Wi-Fi settings.

### 6.3. Plan / Робоча схема ділянки

Робоча схема ділянки є головним екраном у звичайному режимі.

Екран має показувати схематичний план ділянки:

- будинок або інші базові орієнтири;
- межі зон поливу;
- розташування soil sensors;
- розташування water counters;
- поточний стан зон і мінімальні показники об'єктів на самій схемі.

Поверх схеми мають відображатися тільки лаконічні індикатори:

- активна зона поливу, якщо вона відома з поточного стану або останньої дії користувача;
- вологість і температура біля кожного soil sensor;
- витрата води за останні 5 хвилин біля кожного water counter;
- один компактний статусний значок біля сенсора або лічильника, якщо метрики давно не приходили або об'єкт недоступний;
- попередження для зон із критично низькою або надто високою вологістю, якщо їх можна показати без перевантаження схеми.

На самій схемі не треба показувати час останнього оновлення, технічні ids, прив'язки сенсорів до зон, накопичений обсяг води або довгі пояснення. Схема має лишатися максимально лаконічною.

Поза схемою, в компактній панелі стану, показуються:

- стан підключення до контролера;
- короткий стан конфігурації: готова система чи потрібне налаштування;
- поточний або останній відомий тиск;
- швидкий перехід до ручного поливу;
- попередження про критичні або warning/error логи, якщо доступні.

Water counters відображаються на схемі як окремі об'єкти. Біля них показується тільки витрата за останні 5 хвилин. Через можливу затримку метрик UI не повинен показувати water counters як real-time витратомір; якщо дані застаріли або відсутні, поруч із лічильником показується той самий статусний значок, що використовується для недоступних сенсорів.

Робоча схема не повинна перетворюватися на редактор. Вона відповідає за огляд, стан системи і швидкі переходи. Детальна інформація по зоні, сенсору або лічильнику відкривається по кліку на відповідний об'єкт. Редагування геометрії та розташування елементів виконується в окремому режимі.

### 6.4. Zones

Екран зон показує клапани, прив'язані до soil sensors.

Для кожної зони:

- назва;
- pin клапана;
- прив'язаний датчик;
- остання вологість і температура;
- статус доступності сенсора;
- коротке прев'ю або посилання на відповідну область схеми;
- дія ручного відкриття клапана на заданий час.

Ручний полив має перевіряти обмеження `maximumManualValveOpenTimeSeconds` і вимагати підтвердження перед відправкою команди.

### 6.5. Charts

Екран графіків показує історію метрик із server API.

Користувач має обирати:

- сенсор або тип метрики;
- період;
- агрегацію;
- деталізацію bucket.

Для довгих періодів використовуються агреговані series. Raw data варто використовувати тільки для коротких інтервалів.

Вісь часу будується за server timestamp, а не за `uptimeMs` контролера.

### 6.6. Logs

Екран логів має два режими:

- live BLE logs, коли телефон поруч із контролером і підключений через BLE;
- історичні server logs, якщо cloud-функції налаштовані.

Функції:

- фільтр за рівнем;
- фільтр за tag;
- пагінація або дозавантаження історії;
- відкриття конкретного логу з push-сповіщення;
- індикація джерела логу: BLE live або server history.

Push по логах має відкривати цей екран для відповідного пристрою.

### 6.7. Plan Editor / Редактор схеми

Редактор схеми потрібен для створення і зміни графічного плану ділянки.

Він має дозволяти:

- намалювати або розмістити контур ділянки;
- додати схематичний будинок або інші орієнтири;
- намалювати межі зон поливу як прості полігони або області;
- прив'язати кожну область до valve з `valveSettings`;
- розмістити soil sensors на схемі;
- розмістити water counters на схемі;
- прив'язати sensor marker до sensor із `soilSensorSettings`;
- прив'язати water counter marker до water counter settings;
- змінювати назви, кольори або візуальні позначки зон;
- переглянути, які зони, сенсори або лічильники ще не додані на схему.

Редактор має бути достатньо простим для мобільного використання. Для першої версії достатньо схематичного малювання: без точного масштабу, геоданих, супутникових карт або CAD-логіки.

Важливі режими редактора:

- вибір і переміщення елементів;
- малювання зони;
- розміщення сенсора;
- розміщення лічильника води;
- розміщення будинку/орієнтира;
- видалення або скасування останньої дії;
- збереження схеми.

Схема є локальними UI-даними мобільного додатку. Вона не замінює `settings` контролера: клапани, сенсори та їхні технічні прив'язки все одно задаються через controller settings.

### 6.8. Settings

Settings має бути розділений на логічні групи.

Групи:

- Wi-Fi та локальне підключення;
- глобальні правила поливу;
- zones і valves;
- soil sensors;
- pressure sensor;
- water counters;
- схема ділянки;
- cloud/logging;
- service tools.

Збереження controller settings виконується повним snapshot через `PUT /api/settings`. Після успішного збереження додаток має очікувати reboot і перевірити, що контролер знову доступний.

### 6.9. Service Tools

Сервісний розділ потрібен для технічних операцій:

- зміна Modbus slave address;
- перегляд BLE log notifications;
- повторне читання API token;
- повторний пошук IP через BLE;
- діагностика недоступності HTTPS API.

Цей розділ не має бути частиною основного daily-use сценарію.

## 7. Ключові сценарії

### 7.1. Перший запуск

Користувач відкриває додаток, додає контролер через BLE, задає Wi-Fi, чекає reboot, отримує IP/token і переходить до початкового налаштування системи.

Успішний результат: додаток має збережений профіль пристрою і може виконати `GET /api/settings`.

### 7.2. Звичайний запуск

Додаток використовує збережені IP і token та пробує отримати settings.

Якщо контролер доступний, відкривається робоча схема ділянки.

Якщо контролер недоступний, додаток пропонує:

- повторити локальне підключення;
- знайти актуальний IP через BLE;
- перейти до діагностики.

Якщо контролер повертає `401`, додаток має перечитати token через BLE.

### 7.3. Зміна налаштувань

Користувач відкриває settings, додаток завантажує поточний snapshot, користувач змінює параметри, додаток валідовує їх на клієнті та відправляє повний settings object.

Після `restartScheduled: true` UI переходить у стан очікування reboot і не показує старий стан як актуальний.

### 7.4. Ручний полив

Користувач вибирає зону на схемі або у списку зон, задає тривалість, підтверджує дію, додаток відправляє команду `open-for-time`.

Після запуску додаток може оновлювати сенсори для live feedback, але не повинен імітувати стан клапана, якщо API не повертає такий стан явно.

### 7.5. Перегляд графіків

Користувач вибирає метрику і період. Додаток завантажує series із server API і показує графік з коректною агрегацією.

Якщо server API недоступний або cloud не налаштований, додаток пояснює, що історичні графіки потребують серверної інтеграції.

### 7.6. Push по логах

Після реєстрації push token користувач може увімкнути підписку на логи пристрою.

При отриманні push додаток відкриває logs screen і завантажує історію навколо відповідного log event.

## 8. Стани системи

Додаток має явно розрізняти такі стани:

- пристрій не додано;
- BLE scan in progress;
- BLE pairing required;
- Wi-Fi settings saved, reboot expected;
- Wi-Fi ще не отримав IP;
- HTTPS API доступний;
- HTTPS API недоступний;
- token invalid;
- базова конфігурація неповна;
- cloud features disabled;
- server API unavailable.

Стан "базова конфігурація неповна" важливий: контролер може зберегти settings, але автоматичний полив і частина routes можуть не працювати без pressure sensor, magistral water counter, мінімум одного soil sensor та клапанів, прив'язаних до soil sensors.

## 9. Валідація на рівні UI

Додаток має до відправки запитів перевіряти базові обмеження:

- пороги вологості у межах `0..100`;
- стартовий поріг менший за поріг зупинки;
- часові інтервали в допустимому діапазоні;
- коректність watering window;
- унікальність GPIO pins;
- унікальність Modbus addresses для soil sensors;
- відсутність конфлікту address pressure sensor із soil sensors;
- valve посилається на наявний soil sensor;
- duration ручного поливу не перевищує максимум;
- `litersPerTick` є додатним числом.

UI-валідація не замінює server/controller validation, але має зменшити кількість помилкових запитів і пояснювати проблему людською мовою.

## 10. Безпека

Вимоги:

- не логувати `apiAccessToken`, mobile session token, Wi-Fi password і ingest token;
- зберігати controller token у захищеному сховищі мобільної ОС;
- не показувати секрети в UI без явної потреби;
- розділяти controller token, mobile session token і remote ingest token;
- використовувати certificate pinning або перевірку SHA-256 fingerprint для самопідписаного HTTPS endpoint;
- для ручного поливу та перезапусків використовувати явне підтвердження користувача.

## 11. Концептуальний вигляд UI

Візуально додаток має бути схожий на робочий контрольний центр:

- світла або системна тема з хорошою контрастністю;
- компактні інформаційні блоки замість великих декоративних секцій;
- статуси через текст, колір і іконку;
- графіки як основний візуальний елемент history screen;
- ручні дії через зрозумілі кнопки з підтвердженням;
- форми settings згруповані за сенсом, а не за JSON-структурою API.

Головний екран має відповідати на питання:

- чи контролер доступний;
- чи система готова до автоматичного поливу;
- що відбувається на схемі ділянки;
- які зараз ключові показники сенсорів і лічильників на їхніх місцях;
- чи є проблеми;
- яку зону можна швидко відкрити вручну.

## 12. Межі першої версії

У першій версії варто сфокусуватися на:

- одному основному контролері;
- BLE onboarding;
- локальному HTTPS керуванні;
- робочій схемі ділянки;
- редакторі схеми;
- settings;
- zones і ручному поливі;
- базових logs;
- базовій підтримці server metrics/charts, якщо backend готовий.

Не варто на цьому етапі деталізувати:

- складну multi-device організацію;
- ролі користувачів;
- шаринг пристроїв;
- складні automation сценарії поза firmware logic;
- кастомні правила сповіщень, окрім рівня логів і tags;
- детальну дизайн-систему компонентів.

## 13. Критерії готовності концепції

Концепція вважається узгодженою, коли зрозуміло:

- які основні екрани входять у додаток;
- як користувач додає контролер;
- як додаток відновлює доступ після зміни IP або token;
- як виглядає daily-use сценарій на схемі ділянки;
- де налаштовуються сенсори, клапани і правила поливу;
- як запускається ручний полив;
- як показуються логи, графіки та push;
- які дані зберігаються локально;
- які функції належать контролеру, які серверу, а які мобільному клієнту.

Після погодження цього ТЗ його можна розбити на детальні задачі: архітектура Flutter-додатку, моделі даних, BLE service, HTTPS client, secure storage, навігація, робоча схема ділянки, редактор схеми, екрани, валідація, charts, logs і push notifications.
